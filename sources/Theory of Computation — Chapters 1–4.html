Chapter 1
Regular Languages

The simplest machines. No memory. Just pattern recognition — yet surprisingly expressive.

The Vocabulary: Strings, Alphabets, Languages

Every computational problem in this course is phrased as a membership question. Here is why: every problem can be encoded as "does this input string belong to some set L?"

  • An alphabet Σ is any finite set of symbols: {0,1} or {a,…,z}
  • A string is a finite sequence of symbols from Σ. The empty string is ε
  • A language is any set of strings — finite or infinite, simple or complex
💡 Why This Framing? "Is this number prime?" → does its binary encoding belong to {binary representations of primes}?
"Is this program valid C?" → does it belong to {syntactically correct C programs}?
"Is this email spam?" → does it belong to {spam emails}?

Every problem becomes: is this string in this language? The question "what kind of machine do we need?" is the same as "how hard is this language to recognize?"

Deterministic Finite Automata (DFA)

💡 Intuition Imagine the simplest possible computer: reads the input left-to-right, one symbol at a time, maintaining a single "state." When done, it accepts or rejects based solely on that state. It has no memory beyond what state it is currently in. A turnstile (locked/unlocked), a traffic light (red/yellow/green), a vending machine (tracking coins inserted) — all are DFAs.
📐 Formal Definition A DFA is a 5-tuple (Q, Σ, δ, q₀, F):
Q = finite set of states Σ = finite input alphabet δ : Q × Σ → Q // total function: (state, symbol) → next state q₀ ∈ Q // start state F ⊆ Q // set of accept states (enter one of these → accept)
Key: δ is total — defined for every (state, symbol) pair. No undefined transitions. Pure determinism: one input, one path, one outcome.
✏️ Example — Binary Strings with an Even Number of 0s
States: qeven (accept), qodd Start: qeven δ: qeven —0→ qodd qeven —1→ qeven qodd —0→ qeven qodd —1→ qodd // Run on "0110": qeven →⁰ qodd →¹ qodd →¹ qodd →⁰ qeven ✓ ACCEPT
Only 2 states needed! The machine tracks parity of 0s — it has no idea how many total 0s it saw, only whether that count is even or odd.
⚠️ The Key Limitation Finite states = finite memory. A DFA cannot count to an arbitrary number. It cannot recognize {0ⁿ1ⁿ | n≥0} because remembering "how many 0s did I see?" requires arbitrarily large counts — impossible with finitely many states. This will be proved rigorously with the pumping lemma.
🔮 Used Later In... Compilers: the lexer (tokenizer) is a DFA — every keyword, identifier, and number in source code is recognized this way. grep/awk/Python re: your regex patterns compile to DFAs under the hood. All future models: DFA states and transitions are the template — PDAs, TMs, and all variants generalize this exact structure.

Nondeterministic Finite Automata (NFA)

💡 Two Mental Models for Nondeterminism Model 1 — Parallel Universes: When there are multiple choices, the NFA clones itself and explores all paths simultaneously. It accepts if any clone accepts.

Model 2 — Lucky Guesser: The NFA always "guesses" the right transition. If there exists any accepting path through the input, the NFA finds it.

Extra power: NFAs can also take ε-transitions — jump to another state without consuming any input symbol at all.
📐 Formal Definition Same 5-tuple as DFA, but the transition function changes:
δ : Q × Σε → 𝒫(Q) // maps to a SET of next states; ε-transitions allowed Accepts if: at least one active state when input ends is in F
✏️ Example — All Binary Strings Ending in "01"
States: q₁ (start), q₂, q₃ (accept) δ(q₁, 0) = {q₁, q₂} // stay, OR "guess" this 0 starts the final "01" δ(q₁, 1) = {q₁} δ(q₂, 1) = {q₃} δ(q₂, 0) = ∅ δ(q₃, _) = ∅ // Run on "1001": {q₁} →¹ {q₁} →⁰ {q₁,q₂} →⁰ {q₁,q₂} →¹ {q₁,q₃} q₃ ∈ F → ✓ ACCEPT
Notice: if the "guess" is wrong (q₂ dies on a 0), the NFA just loses that branch — other branches survive.
⭐ Key Theorem — NFA = DFA (Subset Construction) Every NFA can be converted to an equivalent DFA.

The trick: Each DFA state tracks a set of NFA states (all the states the NFA could currently be in). If the NFA has n states, the DFA has at most 2ⁿ states (the power set of Q).

Consequence: NFAs and DFAs recognize exactly the same class of languages. NFAs are far more convenient to design — but give no extra computational power. This is the first of many "different formalisms, same class" results.
🔮 Used Later In... Chapter 7 (P vs. NP): Here, nondeterminism gives no extra power (NFA=DFA). In Chapter 7, we ask the same question for polynomial-time TMs — and the answer is unknown. That's P vs. NP. This chapter is where your intuition about nondeterminism is built. Regex engines: The conversion regex → NFA → DFA is the theoretical foundation of every pattern-matching engine ever written.

Regular Expressions

💡 Intuition Instead of drawing a machine with states and transitions, describe what strings look like using algebraic notation. Regular expressions are built from three operations on sets of strings:
Union: R₁ ∪ R₂ — strings in R₁ OR in R₂ Concatenation: R₁ ∘ R₂ — a string from R₁ followed by a string from R₂ Kleene Star: R* — zero or more repetitions of strings from R Base cases: each symbol a ∈ Σ; ε (empty string); ∅ (empty language)
✏️ Examples
0*1* → {ε, 0, 1, 00, 01, 11, 001, 011, 111, ...} (0∪1)*01 → all binary strings ending in "01" (matches our NFA!) (0∪1)* = Σ* → ALL binary strings 0(10)*1 → strings that alternate, starting with 0 and ending with 1: {01, 0101, 010101, ...}
⭐ Key Theorem — Three Formalisms, One Class Regular Expression ↔ NFA ↔ DFA — all three define exactly the same class of languages (the regular languages).

Proof sketch: (1) Each regex operation corresponds to an NFA construction (union: two NFAs with new start state; concatenation: chain ε-transitions; star: loop back with ε). (2) Every DFA can be converted back to a regex via GNFA elimination. The fact that three completely different perspectives converge on the exact same class is a strong signal this is a fundamental, natural class.
🔮 Used Later In... Everywhere in practice: Python re, grep, sed, awk are all implementations of this theory. The equivalence theorem is why they work. Chapter 2: CFGs play the role of "regex for CFLs" — the algebraic-vs-machine equivalence theme repeats throughout the book, each time at a higher power level.

Closure Properties of Regular Languages

Regular languages are closed under: union, concatenation, star, complement, intersection, reversal, difference. "Closed under X" means: if L₁ and L₂ are regular, then L₁ X L₂ is also regular.

💡 Why Closure Under Complement is Surprisingly Easy To complement a DFA: simply swap accept ↔ reject states. That's it. Every state that used to accept now rejects, and vice versa. The DFA runs identically — just the verdict flips. This simplicity is special to DFAs; it does not work so cleanly for PDAs or TMs.
⚠️ Contrast with Chapter 2 CFLs are NOT closed under intersection or complement. This asymmetry is important — it means you can't always combine two CFL constraints into one CFL recognizer. Regular languages' closure under everything makes them very algebraically well-behaved.
🔮 Used Later In... Chapter 4: Proving decidable and recognizable languages are closed under various operations — same technique, same style of proof. Proofs: Intersecting an unknown language with a known regular language (to simplify it) is a common proof technique. If the result is non-regular, the original must be too.

The Pumping Lemma — Proving Nonregularity

💡 The Core Idea — Pigeonhole Gives You a Loop A DFA has n states total. Feed it a string longer than n characters. By the Pigeonhole Principle, it must visit some state twice. That means there's a loop in the computation path. You can traverse that loop any number of times (0, 1, 2, 3, …) and the DFA will still end up in the same state — so it still accepts. This is pumping: repeating the loop.
📐 Pumping Lemma for Regular Languages If L is regular, ∃ pumping length p such that any w ∈ L with |w| ≥ p
can be written as w = xyz satisfying:
1. |xy| ≤ p // the loop occurs in the first p characters 2. |y| ≥ 1 // the pumped part is non-empty (there IS a loop) 3. ∀ i ≥ 0: xy^i z ∈ L // pumping y any number of times stays in L

The Recipe — How to Use It (Proof by Contradiction)

Step 1: Assume L IS regular (for contradiction) Step 2: Let p be the pumping length guaranteed to exist Step 3: YOU choose a string w ∈ L with |w| ≥ p ← choose cleverly! Step 4: For ANY split w = xyz satisfying conditions 1 and 2 (adversary's choice), find some i ≥ 0 such that xy^i z ∉ L Step 5: This contradicts condition 3 → L is not regular ✓
💡 Think of it as a Game You: choose w. Adversary: choose x, y, z (trying to make pumping valid). You: find an i that breaks it. If you can always find such an i regardless of the adversary's split, you win — L is not regular.

The adversary is constrained: |xy| ≤ p and |y| ≥ 1. Your strategy: choose w so that ANY legal split forces y into a "sensitive" part of the string where pumping disturbs the structure.
✏️ Classic Example — {0ⁿ1ⁿ | n ≥ 0} is NOT Regular
// Assume regular with pumping length p Choose: w = 0ᵖ1ᵖ // |w| = 2p ≥ p; and w ∈ L Any legal split w = xyz with |xy| ≤ p and |y| ≥ 1: → xy lies entirely within the first p characters (all 0s!) → y = 0ᵏ for some k ≥ 1 // y is some block of 0s Choose i = 2: xy²z = 0^(p+k) 1ᵖ // p+k zeros, but only p ones → not in L Contradiction! ✓ {0ⁿ1ⁿ} is not regular
Why choose 0ᵖ1ᵖ? Because the |xy| ≤ p constraint forces y to land entirely in the 0-block. The adversary has no room to stretch y across the boundary. So pumping y always breaks the 0-1 balance.
✏️ Another Example — {w | w has equal numbers of 0s and 1s}
Choose: w = 0ᵖ1ᵖ ∈ L // same string works! y must be 0ᵏ for some k ≥ 1 (same reasoning) Pump i=2: 0^(p+k)1ᵖ → more 0s than 1s → not in L Contradiction ✓
🔮 Used Later In... Chapter 2: The CFL pumping lemma uses identical structure (Pigeonhole on computation → find a loop → pump), but on parse trees with two pumped sections. Chapters 4–5: The "assume it's computable, derive a contradiction" structure is the essence of every undecidability proof. Mindset: Thinking rigorously about what a model cannot do is as important as knowing what it can — this mindset carries through the entire course.
Chapter 2
Context-Free Languages

One more piece of memory — a stack — opens up a whole new class. Enough for programming language syntax, not enough for semantic analysis.

Context-Free Grammars (CFG)

💡 Why We Need This — What DFAs Cannot Handle We just proved DFAs can't recognize {0ⁿ1ⁿ}. But matching "n things with n corresponding things" is fundamental: matching parentheses in code, begin/end blocks, opening/closing HTML tags, recursive function call nesting. We need a new idea. The insight: rewriting rules — describe structure, not process.
📐 Formal Definition — CFG A CFG is a 4-tuple (V, Σ, R, S):
V = finite set of variables (non-terminals) — e.g., S, A, EXPR Σ = finite set of terminals — the actual output symbols R = set of production rules: each is A → w (A ∈ V, w ∈ (V ∪ Σ)*) S ∈ V = start variable To derive a string: start with S, repeatedly apply rules (replace any variable with the right-hand side of some rule), until only terminals remain.
✏️ Example — {0ⁿ1ⁿ} via CFG
Rules: S → 0S1 | S → ε Deriving "000111": S → 0S1 → 00S11 → 000S111 → 000ε111 = 000111 ✓ The grammar "wraps" a new 0 on the left and 1 on the right at each step, guaranteeing equal counts. Something a DFA simply cannot do.
The context-free in "context-free": you can replace variable A with w regardless of what surrounds A. Context doesn't constrain the replacement — only the variable itself does.
✏️ Grammar for Arithmetic Expressions
E → E + T | T T → T × F | F F → ( E ) | a This grammar generates expressions like a, a+a, a×a, (a+a)×a, ... It enforces operator precedence: × binds tighter than + because T is "deeper" in the grammar than E.

Parse Trees and Ambiguity

A parse tree represents a derivation as a tree: root = S, internal nodes = variables, leaves (read left-to-right) = the derived string. A grammar is ambiguous if some string has two different parse trees.

⚠️ Ambiguity — A Real Problem in Compilers In a compiler, two parse trees = two different interpretations of the same code. 2 + 3 × 4 should mean 14 (not 20) — but an ambiguous grammar makes both valid. Languages like C and Java are carefully designed with unambiguous grammars. Remarkably, determining whether a given CFG is ambiguous is undecidable (Ch. 5).
🔮 Used Later In... Compilers: Every programming language syntax is defined by a CFG. The parser (phase 2 of compilation, converting tokens into a parse tree) is built directly from it. ANTLR, yacc, bison — all are CFG-based parser generators. Chapter 4: Problems about CFGs (is this language empty? finite?) are decidable building blocks. Chapter 5: CFG ambiguity is a canonical undecidable problem proved via reduction.

Chomsky Normal Form (CNF)

Every CFG can be converted to an equivalent CFG in Chomsky Normal Form: every production rule is either A → BC (two variables) or A → a (one terminal). Only the start variable may derive ε via S → ε.

💡 Why CNF — It Makes Trees Predictable In CNF, every parse tree for a string of length n has exactly 2n−1 internal nodes. This makes the tree's size predictable and bounded. This clean structure enables two critical results:

1. CYK Algorithm: Dynamic programming parser for any CFL in O(n³) time — requires CNF to guarantee a clean recurrence.
2. CFL Pumping Lemma: A parse tree in CNF that is "tall enough" must have a repeated variable (Pigeonhole) — that repeated variable is the source of pumping.
🔮 Used Later In... Directly in the proof of the CFL pumping lemma (this chapter). The CYK algorithm appears in NLP parsers and some compiler tools. The conversion technique (eliminating ε-rules, unit rules, long rules) is standard preprocessing in formal language tools.

Pushdown Automata (PDA)

💡 Intuition — NFA with a Stack Take an NFA. Add a stack: an unbounded last-in-first-out memory. At each step, the machine can read (or not) the next input symbol, pop the stack top, and push any string onto the stack.

Why a stack? Context-free languages have nested recursive structure. A stack is the perfect tool: push when entering a nested layer, pop when leaving. The stack remembers an unbounded amount of information — but only in LIFO order. This is the one key memory primitive CFLs need.
📐 Formal Definition — PDA A PDA is a 6-tuple (Q, Σ, Γ, δ, q₀, F):
Γ = stack alphabet (may differ from input alphabet Σ) δ : Q × Σε × Γε → 𝒫(Q × Γε) ↑read input? ↑pop stack? ↑(new state, push onto stack) PDAs are nondeterministic by definition.
✏️ Example — {0ⁿ1ⁿ} via PDA
Phase 1 (reading 0s): push a marker onto the stack for each 0 read Phase 2 (reading 1s): pop one marker for each 1 read Accept if: input exhausted AND stack is empty simultaneously Reject if: try to pop from empty stack, or input left with stack empty, etc. The stack acts as an unbounded counter — something a DFA's finite states cannot do!
✏️ Example — Balanced Parentheses
On '(': push '(' onto stack On ')': if stack is non-empty, pop; else reject At end: if stack empty → ACCEPT; else → REJECT Works for any nesting depth — the stack "remembers" every unclosed '('
⭐ Key Theorem — CFG = PDA Context-free grammars and pushdown automata are equivalent — they recognize exactly the same class of languages (the context-free languages).

CFG → PDA: Build a PDA that "simulates" a leftmost derivation. The stack holds the remaining portion of the current sentential form (yet to be derived). At each step: if the top is a variable, nondeterministically apply a grammar rule; if the top is a terminal, verify it matches the next input symbol.

PDA → CFG: Each pair of states (the state before pushing, the state after popping) defines a grammar variable. The resulting grammar encodes the PDA's behavior.
⚠️ Deterministic PDAs are Strictly Weaker Unlike DFAs vs. NFAs (where they're equivalent), deterministic PDAs cannot recognize all CFLs. For example, palindromes over {a,b} require nondeterminism to "guess" the midpoint. This asymmetry matters: DPDAs correspond to languages parseable without backtracking (LR/LL parsing). Full CFLs may require nondeterminism.
🔮 Used Later In... Compilers: LR(k) and LL(k) parsers — the engines behind yacc, bison, ANTLR, and every production parser — are deterministic PDAs. The parser in your compiler is literally this theory in action. Chapter 3: Turing Machines are the next step: replace the stack with an infinite read/write tape. The progression DFA → PDA → TM is all about what kind of memory you add and how you access it.

The Pumping Lemma for CFLs

💡 Intuition — Pigeonhole on Parse Trees A CFG has |V| variables. A parse tree in CNF for a string of length n has height at least log₂(n). When n is large enough (n > 2^|V|), some variable must appear twice on some root-to-leaf path (Pigeonhole). A repeated variable means the parse tree contains a "loop" — a subtree structure that can be repeated (pumped) any number of times. Because the loop appears between two copies of the same variable, you pump two sections simultaneously (one on each "side" of the nested structure).
📐 CFL Pumping Lemma — Statement If L is a CFL, ∃ pumping length p such that any w ∈ L with |w| ≥ p
can be written as w = uvxyz where:
1. |vy| ≥ 1 // at least one of the two pumped sections is non-empty 2. |vxy| ≤ p // the middle portion is bounded 3. ∀ i ≥ 0: uv^i xy^i z ∈ L // pump BOTH v and y together
Notice: you pump two substrings simultaneously (v and y), not one. This reflects the two "sides" of the loop in the parse tree. The regular pumping lemma is a special case with one pumped section.
✏️ Classic Example — {aⁿbⁿcⁿ | n ≥ 0} is NOT a CFL
// Assume CFL with pumping length p Choose: w = aᵖbᵖcᵖ // |w| = 3p ≥ p; w ∈ L Any legal split w = uvxyz with |vxy| ≤ p and |vy| ≥ 1: → vxy spans at most p consecutive characters → So vxy can contain at most 2 distinct symbol types Case 1: vxy ⊆ aᵖbᵖ (contains only a's and/or b's) Pump i=2: more a's and/or b's, same number of c's → not in L ✗ Case 2: vxy ⊆ bᵖcᵖ (contains only b's and/or c's) Pump i=2: more b's and/or c's, same number of a's → not in L ✗ Either way: contradiction ✓ {aⁿbⁿcⁿ} is not a CFL
Why this language matters: It's the simplest "three-way counting" language. Compilers check many constraints simultaneously (type safety, scope rules, arity) — these are fundamentally beyond CFL expressibility and require a separate semantic analysis phase.
✏️ Another Example — {ww | w ∈ {a,b}*} is NOT a CFL
Choose: w = aᵖbᵖaᵖbᵖ Any split uvxyz with |vxy| ≤ p must lie within one "quadrant" Pumping disturbs the pattern in that region but not the others → the two halves of ww diverge → not in L Contradiction ✓
🔮 Used Later In... Chapters 4–5: The proof structure (find a loop via Pigeonhole, pump to derive contradiction) is the template for diagonalization and reduction arguments in undecidability. Compilers: Understanding CFL limitations explains why compilers need a semantic analysis phase beyond parsing — type checking and scoping are not context-free problems.

Closure Properties of CFLs

CFLs are closed under: union, concatenation, Kleene star.
CFLs are NOT closed under: intersection or complement.

✏️ Key Counterexample — Intersection
L₁ = {aⁿbⁿcᵐ | n,m ≥ 0} ← CFL (count a's matched to b's) L₂ = {aᵐbⁿcⁿ | n,m ≥ 0} ← CFL (count b's matched to c's) L₁ ∩ L₂ = {aⁿbⁿcⁿ | n ≥ 0} ← NOT a CFL (proved above!) Two individually easy problems → their intersection is hard.
⚠️ But CFL ∩ Regular = CFL Even though CFLs aren't closed under CFL∩CFL intersection, they ARE closed under intersection with a regular language. (Run the PDA and DFA in parallel.) This is a useful tool in proofs and in compiler design: you can filter a CFL with regex constraints and stay in the CFL class.
🔮 Used Later In... Chapter 4: Decidable languages ARE closed under intersection and complement — a key difference that gives decidable languages much better algebraic structure. The contrast between CFL closure properties and decidable language closure properties is important when categorizing problems by complexity.
Chapter 3
The Church-Turing Thesis

The ceiling of computation. The theoretical model of what a "computer" actually is.

Turing Machines

💡 The Big Leap From PDAs A DFA: read-only, left-to-right. A PDA: adds a LIFO stack. A Turing Machine: replaces the stack with an infinite read/write tape. The head can move left or right and read or write at any position. This gives three new powers:

1. Unlimited memory — the tape is infinite
2. Read AND write — it can modify what's already there
3. Random access — the head can go left to revisit earlier tape positions

The tape serves as both the input medium and unlimited working memory. This is why TMs can compute anything a real computer can.
📐 Formal Definition — Turing Machine A TM is a 7-tuple (Q, Σ, Γ, δ, q₀, q_accept, q_reject):
Q = finite set of states Σ = input alphabet (does NOT contain blank ⊔) Γ = tape alphabet: Σ ⊆ Γ, ⊔ ∈ Γ δ : Q × Γ → Q × Γ × {L, R} ↑ state+tape symbol → new state, write symbol, move L or R q₀ ∈ Q = start state q_accept ∈ Q = unique accept state (enter this → halt and accept) q_reject ∈ Q = unique reject state (enter this → halt and reject) q_accept ≠ q_reject
⚠️ Three Possible Fates — This is the Heart of Chapter 4 On any input, a TM can do one of exactly three things:
ACCEPT: enters q_accept → w is in the language REJECT: enters q_reject → w is not in the language LOOP: runs forever → never decides either way
A TM that always halts (never loops) is called a decider. Not all TMs are deciders. Identifying which languages have deciders vs. only recognizers is the central topic of Chapter 4.
📐 Two Critical Definitions
Turing-recognizable (recursively enumerable): L is recognized by some TM — it accepts all strings in L, but may loop forever on strings NOT in L. Turing-decidable (recursive): L is decided by some TM that always halts — it accepts strings in L and rejects strings NOT in L. Decidable ⊂ Recognizable (Chapter 4 shows this inclusion is strict)
✏️ Example — {w#w | w ∈ {0,1}*}
Algorithm (high-level description): 1. If input contains no #, reject. 2. Zig-zag: mark the first unmarked symbol on the left of #. Cross to the right of # and find the corresponding position. If symbols match, mark both; else reject. 3. Repeat until all left-side symbols are marked. 4. If all right-side symbols are also marked → ACCEPT; else REJECT. Key: the TM head moves left AND right repeatedly. It crosses the string multiple times, using marked symbols as "memory" on the tape itself. A DFA or PDA could never do this systematic cross-referencing.
🔮 Used Later In... All of Chapters 4–7. Every concept from here on is built on TMs. Chapter 4: A TM can be given another TM's description as input and simulate it — this gives us the Universal TM, which directly leads to the Halting Problem proof. Chapter 7: TMs with polynomial time bounds become the definition of P and NP.

Variants of Turing Machines

Many natural extensions of the basic TM exist. The profound result: they are all equivalent in power. This strongly supports the Church-Turing Thesis.

Multitape TMs

📐 k-Tape TM Has k tapes, each with its own independent read/write head. Much more convenient to program: dedicate one tape to input, one to output, one to scratch work.
Theorem: Every k-tape TM can be simulated by a 1-tape TM. Idea: interleave all k tapes onto one tape (separated by markers); simulate each head. Cost: t steps on k-tape TM → O(t²) steps on 1-tape TM. Polynomial slowdown.
🔮 Used Later In... Chapter 7: The polynomial slowdown means k-tape TMs don't change the class P. If an algorithm runs in polynomial time on a k-tape TM, it runs in polynomial time on a 1-tape TM (just with a larger polynomial). Polynomial-time results are robust to this kind of engineering convenience.

Nondeterministic TMs (NTM)

📐 Nondeterministic TM At each step, can branch into multiple possible next states. Accepts if ANY branch accepts.
Theorem: Every NTM can be simulated by a deterministic TM. Idea: breadth-first search through all computation branches (use 3 tapes). Cost: t steps on NTM → potentially exponential steps on DTM.
⭐ This is the P vs. NP Seed 🌱 For unrestricted TMs: nondeterminism adds no power (NTM = DTM). They recognize the same languages. But the simulation may take exponentially more time.

For polynomial-time TMs:
  • P = languages decidable in polynomial time by a deterministic TM
  • NP = languages decidable in polynomial time by a nondeterministic TM

The question: can the exponential simulation blowup be avoided for all NP problems? That is P vs. NP — the biggest open problem in all of computer science.

Enumerators

A TM with an attached "printer." It runs indefinitely, printing strings one by one. A language is Turing-recognizable if and only if some enumerator enumerates it. This gives an intuitive picture of "recursively enumerable": you can list all strings in L (even if the list is infinite), but you might wait forever for a particular string to appear — or never know if it won't.

The Church-Turing Thesis

⭐ The Thesis (This Is Not a Theorem) Every reasonable model of computation is equivalent to a Turing Machine.
💡 Why It's a Thesis and Not a Theorem "Reasonable" and "computation" are informal, intuitive notions — you can't formally prove a claim about them. The evidence is overwhelming: lambda calculus (Church, 1936), recursive functions (Kleene), register machines, RAM models, actual CPUs, cellular automata, DNA computing, quantum computing (for decision problems)... all have been proven equivalent to TMs. In 80+ years nobody has found a more powerful "reasonable" model.

So we accept the thesis as a definition of "computation."

The thesis allows us to say: "An algorithm exists if and only if a Turing Machine for it exists." When Chapter 4 proves a problem is TM-undecidable, the Church-Turing Thesis lets us conclude it is unsolvable by any possible algorithm — in any programming language, on any hardware. Without this thesis, results would only apply to TMs specifically.

Practically, the thesis justifies high-level TM descriptions: instead of specifying every state and transition, we describe algorithms naturally ("on input G: run BFS, check connectivity..."). Any clearly implementable algorithm corresponds to a valid TM.

🔮 Used Later In... Every result in Chapters 4–7 that says "no algorithm exists" or "this is computable" implicitly relies on this thesis. It is the bedrock. Without it, computability and complexity theory would be a statement about one specific formalism (TMs) rather than computation itself.
Chapter 4
Decidability

We now have the most powerful computational model imaginable. So: what can't it do? Chapter 4 answers this — and the answer is shocking.

The Enabling Idea: Machines as Strings

💡 The Key Conceptual Leap Everything in Chapter 4 rests on one idea: a Turing Machine can be encoded as a string. Once a TM is just a string, you can feed it as input to another TM. Machines can reason about other machines. This "self-reference" is the door to both powerful results and paradox.

Think of it this way: a Python program is just a text file. You can write a Python program that reads another Python program as input and analyzes it. TMs are exactly the same — except we now have theorems about what such analysis can and cannot do.

We write ⟨M⟩ for the string encoding of TM M, and ⟨M, w⟩ for the encoding of the pair (TM M, input string w). The exact encoding doesn't matter much — only that it exists and is reasonable. From here on, TMs take other TMs as inputs routinely.

The Universal Turing Machine (UTM)

⭐ The Universal TM There exists a TM U such that on input ⟨M, w⟩, U simulates M running on w — and accepts iff M would accept w.

U is the theoretical ancestor of every stored-program computer. The idea that a machine can interpret another machine's description as data, and execute it, is the foundation of modern computing. Every CPU you have ever used is a physical implementation of this idea.

Consequence: The language A_TM = {⟨M, w⟩ | M is a TM and M accepts w} is Turing-recognizable — the UTM recognizes it. But is it decidable? That is the central question of this chapter.
🔮 Connection Back to Ch. 3 In Chapter 3 we introduced TMs and their three outcomes: accept, reject, loop. The UTM exposes the problem: when U simulates M on w, if M loops forever, U also loops forever. U cannot simply "wait and see" whether M will halt — it must wait indefinitely. This is why the UTM only recognizes A_TM but does not decide it.

Decidable Problems About Regular Languages

Before hitting the impossible, let's see what IS decidable. Starting with the simplest class: DFAs.

📐 Three Decidable Problems
A_DFA = {⟨M, w⟩ | M is a DFA and M accepts w} DECIDABLE E_DFA = {⟨M⟩ | M is a DFA and L(M) = ∅} DECIDABLE EQ_DFA = {⟨M₁,M₂⟩ | M₁,M₂ are DFAs and L(M₁) = L(M₂)} DECIDABLE
✏️ Why A_DFA is Decidable — Run It and Wait
Decider for A_DFA: On input ⟨M, w⟩: 1. Simulate M on w 2. If M ends in an accept state → ACCEPT If M ends in a non-accept state → REJECT Why this works: M is a DFA. DFAs always halt (they read input left-to-right, one step per symbol). So our decider always halts too. Simple — but notice this uses nothing special about DFAs other than the fact that they always halt.
✏️ Why E_DFA is Decidable — Graph Reachability
Decider for E_DFA: On input ⟨M⟩: 1. Mark the start state q₀ 2. Mark any state reachable (by any symbol) from a marked state 3. Repeat until no new states get marked 4. If any accept state is marked → REJECT (language is non-empty) If no accept state is marked → ACCEPT (language is empty) Intuition: L(M) = ∅ iff no accept state is reachable from q₀. This is just a graph reachability problem — classic BFS/DFS on the DFA's state graph.
✏️ Why EQ_DFA is Decidable — Symmetric Difference
Key insight: L(M₁) = L(M₂) iff L(M₁) △ L(M₂) = ∅ where △ is symmetric difference: (L₁ \ L₂) ∪ (L₂ \ L₁) Decider for EQ_DFA: 1. Construct DFA C recognizing L(M₁) △ L(M₂) (regular languages closed under complement, union, intersection → can do this) 2. Run the E_DFA decider on ⟨C⟩ 3. If L(C) = ∅ → ACCEPT (the two languages are identical) else → REJECT This uses closure properties of regular languages (Chapter 1) as a tool!
🔮 Why This Section Matters These proofs establish the pattern for all decidability proofs: describe an algorithm, argue it always halts, argue it is correct. The tools come from earlier chapters (closure properties, graph reachability, CFG algorithms). Chapter 4 is where everything you learned in Ch. 1–3 becomes ammunition for new proofs.

Decidable Problems About Context-Free Languages

📐 Two Key Decidable Problems
A_CFG = {⟨G, w⟩ | G is a CFG and G generates w} DECIDABLE E_CFG = {⟨G⟩ | G is a CFG and L(G) = ∅} DECIDABLE
✏️ Why A_CFG is Decidable — CYK Algorithm
Decider for A_CFG: On input ⟨G, w⟩: 1. Convert G to Chomsky Normal Form (CNF) 2. Run the CYK parsing algorithm on w CYK is dynamic programming on substrings: Can variable A derive substring w[i..j]? Base: A → a iff w[i] = a Step: A → BC iff ∃ split k: B derives w[i..k] AND C derives w[k+1..j] Answer: G generates w iff S derives w[1..|w|] Runtime: O(n³ · |G|) — always halts, always correct. ✓ Why CNF matters: without it, derivations could be infinite (via A → A).
✏️ Why E_CFG is Decidable — Mark Variables That Generate Terminals
Decider for E_CFG: On input ⟨G⟩: 1. Mark every terminal symbol a ∈ Σ as "generatable" 2. If rule A → w and every symbol in w is marked → mark A 3. Repeat until no new variables get marked 4. If S is marked → REJECT (L(G) ≠ ∅) If S is not marked → ACCEPT (L(G) = ∅) Intuition: we propagate "can generate a terminal string" bottom-up through the grammar rules. If S can eventually generate a string, L(G) ≠ ∅.
⭐ Corollary — Every CFL is Decidable Since A_CFG is decidable, for any specific CFL L generated by grammar G:
Given input w, run the A_CFG decider on ⟨G, w⟩. It always halts. Therefore every CFL has a decider.

The hierarchy of decidability so far:
Regular ⊆ Context-Free ⊆ Decidable ⊆ Turing-Recognizable
⚠️ EQ_CFG is Undecidable Unlike EQ_DFA, the problem of testing whether two CFGs generate the same language is undecidable. Proved in Chapter 5 via reduction from A_TM. The closure-under-complement trick doesn't work here — because CFLs are NOT closed under complement. The asymmetry between Ch. 1 and Ch. 2 closure properties comes back to bite us.
🔮 Why This Matters The decidability of A_CFG is used in compiler verification. The undecidability of EQ_CFG means you cannot, in general, automatically check whether two grammars (say, two versions of a programming language specification) define the same language. This has real software engineering implications.

A_TM — The Central Undecidable Language

💡 Setup — Why A_TM is the Key Everything so far has been decidable: DFA acceptance, DFA emptiness, CFG generation. Now we ask the natural next question: what about TM acceptance?

A_TM = {⟨M, w⟩ | M is a TM and M accepts w}

We already know A_TM is Turing-recognizable (the UTM recognizes it — simulate M on w, accept if M does). The question is: is A_TM decidable? Can we always get a definite yes/no answer?

The answer is NO — and this is one of the most important theorems in all of mathematics.
⭐ Theorem — A_TM is Undecidable There is no Turing Machine that decides A_TM. No algorithm can, in general, determine whether an arbitrary TM accepts an arbitrary input.

This is equivalent to the Halting Problem: no algorithm can determine whether an arbitrary TM halts on an arbitrary input. (A_TM and H_TM are equivalent via simple reductions.)
⚠️ What This Actually Means This is not a limitation of current computers, programming languages, or mathematical techniques. It is a fundamental, absolute mathematical result: no possible algorithm — running on any computer, in any language, with unlimited time and memory — can solve this problem in general. It is mathematically impossible, as firmly as it is impossible to trisect an arbitrary angle with ruler and compass.

The Diagonalization Proof

💡 Where This Idea Comes From — Cantor (1874) Georg Cantor proved that the real numbers are "more infinite" than the natural numbers — you cannot list all real numbers in a sequence. His trick: suppose you had such a list. Construct a new real number that differs from the n-th number in the n-th decimal digit, for every n. This new number cannot be anywhere on the list. Contradiction.

Turing applied the same idea to computation: construct a TM that does the opposite of what any alleged decider would do on its own description. Contradiction.
📐 The Proof — Step by Step
// Assume for contradiction that A_TM is decidable. // Let H be a TM that decides A_TM: H(⟨M, w⟩) = ACCEPT if M accepts w H(⟨M, w⟩) = REJECT if M does not accept w (always halts) // Construct a new TM D using H as a subroutine: D(⟨M⟩): Run H on ⟨M, ⟨M⟩⟩ // ask: "does M accept its own description?" If H accepts → REJECT // D does the opposite If H rejects → ACCEPT // D does the opposite // Now ask: what does D do on input ⟨D⟩? D(⟨D⟩) accepts iff H(⟨D, ⟨D⟩⟩) rejects iff D does NOT accept ⟨D⟩ D(⟨D⟩) accepts iff D(⟨D⟩) does not accept ← CONTRADICTION // Therefore H cannot exist. A_TM is undecidable. ∎
💡 The Diagonal Visualized Imagine a table: rows are all TMs M₁, M₂, M₃, …; columns are all TM descriptions ⟨M₁⟩, ⟨M₂⟩, ⟨M₃⟩, …; cell (i, j) = "does Mᵢ accept ⟨Mⱼ⟩?" (✓ or ✗).

H would let us fill in this table perfectly. D reads the diagonal — cell (i,i) = "does Mᵢ accept its own description?" — and flips every entry. D's behavior cannot match any row in the table (it differs from row i in column i). But D is itself a TM, so it must appear as some row. Contradiction.

This is identical to how Cantor's new real number differs from every number in the list. The structure is exactly the same.
💡 The Liar's Paradox Connection The contradiction has the flavor of the ancient Liar's Paradox: "This sentence is false." If it's true, it's false. If it's false, it's true. D is designed to create this paradox for computation: D accepts its own description iff it rejects its own description. The lesson: self-reference, when combined with the ability to simulate, creates unavoidable paradoxes that mark the limits of computability.
🔮 Used Later In... Chapter 5 (Reductions): The direct proof via diagonalization only works for A_TM. For the dozens of other undecidable problems (halting problem on a blank tape, Post Correspondence Problem, CFG equivalence, etc.), we use reductions: show that if you could solve problem X, you could solve A_TM — but we know you can't solve A_TM, so you can't solve X either. Reductions are the main proof technique of Ch. 5. | Rice's Theorem: A powerful generalization that says any non-trivial property of TMs' languages is undecidable. Covers infinitely many problems in one theorem.

Recognizable vs. Co-Recognizable vs. Decidable

A New Definition

A language L is co-Turing-recognizable if its complement L̄ is Turing-recognizable. This gives us a three-way classification for languages.

⭐ Key Theorem — The Characterization of Decidability A language L is decidable if and only if L is both Turing-recognizable and co-Turing-recognizable.
Proof (→): If L is decidable, then the decider accepts L and rejects L̄. Reversing accept/reject gives a decider for L̄. So L is recognizable (by the decider) and L̄ is recognizable (by the reversed decider). ✓ Proof (←): Suppose TM M₁ recognizes L, and TM M₂ recognizes L̄. Build a decider for L: on input w, run M₁ and M₂ in parallel (interleave their steps). Eventually one must accept: - If M₁ accepts → w ∈ L → ACCEPT - If M₂ accepts → w ∈ L̄ → REJECT This always halts because every w is in either L or L̄. ✓
💡 Why the Parallel Simulation Works The key insight in the (←) direction: we don't run M₁ to completion, then run M₂. We interleave them — run one step of M₁, then one step of M₂, then one step of M₁, etc. This way, if either one accepts (at any point), we catch it immediately. And since w must be in L or L̄ (not both), eventually one of the two recognizers must accept. The decider never loops.
⭐ Corollary — The Complement of A_TM is NOT Turing-Recognizable
Proof: A_TM is Turing-recognizable (the UTM recognizes it). A_TM is NOT decidable (proved above by diagonalization). If A̅_TM were also recognizable, then by the theorem above: A_TM is recognizable AND A̅_TM is recognizable → A_TM would be decidable. ← Contradiction! Therefore A̅_TM is NOT Turing-recognizable. ∎
This means: no TM can even enumerate all the ⟨M,w⟩ pairs where M does NOT accept w. The non-accepting pairs are, in a precise sense, "more unrecognizable" than the accepting ones.

⭐ The Big Picture Summary for Chapter 4 What Chapter 4 establishes:
  • The boundary between decidable and undecidable is real and provable
  • Simple problems about DFAs and CFGs are decidable (using Ch. 1–3 results as tools)
  • The fundamental problem of TM acceptance (A_TM) is undecidable — proved by diagonalization
  • Decidability = recognizable + co-recognizable (the parallel simulation theorem)
  • A_TM is recognizable; its complement is not even recognizable
🔮 What Comes in Chapter 5 Chapter 5 introduces reductions: the main tool for proving that specific problems are undecidable. Instead of re-doing a diagonalization argument for every new problem, you show: "if I could solve problem X, I could solve A_TM — but I can't solve A_TM, so I can't solve X." This lets us cascade the undecidability of A_TM to hundreds of natural problems. Rice's Theorem alone makes every non-trivial semantic property of TMs undecidable in a single sweep.
